开发文档

本页描述 tg_transfer_bot 的真实代码边界、运行时数据流和扩展方式。修改功能时，先确定它属于交互层、任务层、持久化层还是运行时上下文。

按钮与命令复用同一业务入口 数据库状态驱动恢复 先复现再修复

架构分层

项目不是把 TDLib 调用直接写在按钮 handler 里，而是通过交互、任务、数据和运行时四层传递明确的数据结构。

交互层 tgbot.rs、command/、send/
解析消息、callback 和输入状态，只负责展示与控制。
→
任务层 workflow/、spawn.rs
创建、复用、恢复任务，编排下载、准备、上传和终态。
→
持久化层 store/、db/
以任务、子项、缓存、结果和运行配置为边界读写数据库。

核心共享状态

对象位置用途
AppContextapp_context.rs持有运行时配置、下载/上传进度、single-flight、执行锁、授权集合。
BotConfigconfig.rs启动级配置和从数据库回填的运行态配置。
RequestActorconfig.rs明确当前请求 chat、用户和权限校验边界。
TransferPlantransfer/types.rs把源链接、目标和来源 client 组合成可执行计划。

启动链

启动顺序不能随意调整：数据库运行态必须先完成 migration 和 seed，再创建 TDLib 接收循环。

transfer_bot/src/lib.rs
main
  -> transfer_bot::run()
     -> parse CLI and config.json
     -> init tracing
     -> init business database URL
     -> run SeaORM migrations
     -> load or seed runtime config / targets / access
     -> build AppContext
     -> create bot and user TDLib clients
     -> tgbot::receive(app_context, config)
  1. config.json 只提供启动级秘密、TDLib 目录、登录方式和默认值。
  2. bootstrap_runtime_database_state 执行 migration，并读取或 seed 运行配置、目标和授权名单。
  3. 数据库值回填到 BotConfig，同时写入 AppContext 的运行时状态。
  4. TDLib client 就绪后启动恢复、进度刷新和文件 GC 等后台服务。
不要绕过启动链 测试如果只创建表、不执行 runtime seed，容易出现“测试通过但实际启动缺少默认配置”的假阳性。

Update 分发

tgbot.rs 是 TDLib update 的总入口。每种 update 先按 client_id 和类型分类，再进入对应业务边界。

Update处理内容关键边界
AuthorizationState登录状态机Bot token 与 User 登录方式不同，但都必须先 ready。
NewMessage命令、链接、媒体和回复只接受交互 client 的私聊；User client 不处理 Bot 菜单。
NewCallbackQuery按钮 callback先 ACK，再校验 actor 和输入草稿归属。
UpdateFile下载/上传字节进度按 client_id + TDLib file id 更新运行时映射。
MessageSendSucceeded发送消息确认唤醒等待者并登记最终消息媒体 File ID。
处理原则
receive loop
  -> identify client role
  -> classify update kind
  -> update runtime progress / message waiter
  -> authorize actor when interaction is required
  -> dispatch command or callback
  -> render one current card when possible

交互开发

按钮交互和命令必须最终落到同一条业务写入路径。按钮只负责收集输入、确认和导航，不复制命令逻辑。

菜单输入生命周期

  1. 按钮 callback 创建或更新 menu_input_draft，并记录 request chat 与 sender user。
  2. 发送一条 ForceReply 或原生聊天/用户选择器提示，并记录当前提示消息 ID。
  3. 用户回复后由 menu/input/state.rs 校验步骤、actor 和超时。
  4. 输入模块把结构化值交给 simple.rs、target.rs 或 admin.rs。
  5. 阶段切换时删除过时 picker/card，尽量复用或更新同一条进度消息。
需求应修改的位置不要修改的位置
新增菜单入口menu/keyboard/、menu.rs不要在 update loop 中手写按钮 JSON。
新增输入步骤menu/input/state.rs、对应 input handler不要用全局变量保存用户输入。
减少消息刷屏提示消息 tracker、删除/编辑 helper不要在每个阶段无条件 send 新消息。
新增命令命令模块、统一 command router、help descriptor不要让按钮拥有另一套业务语义。

转存状态机

一次转存由主任务和多个子项组成。主任务负责请求级状态，子项负责每条源消息的准备和结果。

建立计划解析源、目标和来源 client
查重/恢复按 source + target 判断复用、运行中或恢复
准备子项读取消息、查缓存、下载并构造输入内容
上传登记临时和最终 File ID，更新上传字节
终态落库保存结果地址、释放文件引用和进度卡

主任务状态

pending → running → success / failed / partial；人工停止会经过 cancelling → cancelled，暂停则经过 paused → running。

子项状态

pending → preparing → prepared → uploading → success；准备或上传异常进入 failed，用户停止进入 cancelled。恢复对齐后消失的相册项标记为 obsolete。

控制点 runner.rs 在准备前、下载后、准备后和上传前检查 pause/stop。新增耗时步骤时必须保留这些安全点，否则按钮状态会滞后。

数据与缓存

业务数据库和 TDLib 自有数据库分离。业务表用于恢复和可观察性，TDLib 目录只保存 Telegram client 自身状态与媒体文件。

实体作用修改注意事项
transfer_job一次完整转存请求状态、去重、结果入口和恢复依据。
transfer_item任务中的单条源消息子项状态、错误和 file owner。
file_cache跨任务媒体去重和延迟删除主键是 owner role + file key，引用归零才能进入 GC。
transfer_result_message保存一个任务的多个目标消息入口album 分组不能只保存首个结果。
menu_input_draft持久化未完成交互必须绑定 request chat、sender user 和步骤。
authorized_user动态授权及名称快照权限判断使用 user_id，名称只用于展示。

缓存命中规则

  1. 从消息提取 TDLib remote unique id，作为稳定 file_key。
  2. 使用实际源 client 的 role 查询 file_cache，不能跨 Bot/User 复用本地 file id。
  3. 只有 status=ready、active_refs > 0、local_path 非空且文件真实存在才命中。
  4. 命中后构造 InputFile::Local；未命中才调用 TDLib 下载。
  5. 新增缓存状态时同步更新状态模块、GC、健康统计和测试 fixture。

进度与消息生命周期

下载进度来自 TDLib File 的 local 字段，上传进度来自发送消息后的 remote File。两者都按 client 隔离。

进度类型运行时索引常见错误
下载(client_id, td_file_id)把 Bot 和 User 的同一个 file id 当成共享状态。
上传job + item 逻辑项，再反向映射当前 File ID临时 File ID 和最终 File ID 被统计成两个文件。
发送等待client_id + chat_id + message_id发送成功后重复补发第二张结果卡。
输入提示草稿 key + picker message id阶段切换后旧 ForceReply 或 picker 继续留在会话中。

进度卡优先通过 edit 更新；只有没有可编辑的旧消息时才 send 新卡。最终消息的 File ID 仍需登记，以接收迟到的 UpdateFile。

权限模型

权限主体是 Telegram 用户，不是当前群组。所有需要交互的请求都要验证私聊边界和 sender user id。

主体来源权限
Ownerowner_user_id全部操作，包括授权管理。
静态管理员admin_user_ids转存、查询、任务和运行态配置。
动态管理员authorized_user 表及 AppContext与静态管理员相同，除授权管理外。
未授权用户不在上述集合拒绝交互并返回联系管理员提示。

新增权限检查时复用 access 模块和 RequestActor。不要根据 chat_id 推断用户身份，也不要让 User client 代替 Bot 处理管理交互。

扩展步骤

新增一个按钮功能

  1. 在对应 keyboard/spec 模块增加按钮和 callback payload。
  2. 在 callback router 增加纯决策分支，并先 ACK callback。
  3. 如果需要输入，创建明确的 draft step 和 actor 校验。
  4. 把结构化输入转交给现有命令或 store 函数，避免另写一套业务写入。
  5. 阶段切换时删除过时的 picker/card，并补充按钮布局和路由测试。

新增一个数据库字段

  1. 更新 SeaORM entity 和 ActiveModel。
  2. 新增 migration，保证 SQLite/PostgreSQL 都能执行。
  3. 更新 runtime_schema/ 与测试 schema 探针。
  4. 修改 store 查询、插入、更新和恢复逻辑。
  5. 加入迁移幂等、旧数据和完整业务链测试。

新增可观测字段

先确定字段属于持久化快照还是运行时快照，再同步更新 render/text、详情页和首页摘要。不要在展示层临时查询整张数据库表。

测试与调试

修复问题时遵循“复现 → 最小测试 → 修复 → 完整回归”的顺序。测试应描述用户可观察的行为，而不是私有实现细节。

本地检查命令

PowerShell
$env:LOCAL_TDLIB_PATH = "F:/tdlib/td/tdlib"
cargo fmt --all -- --check
cargo test -p transfer_bot --lib
cargo clippy -p transfer_bot --all-targets --no-deps -- -D warnings
cargo build -p transfer_bot
git diff --check

测试分层

测试类型适用场景重点
纯单元测试callback payload、状态决策、文案和键盘布局快、确定，不依赖 TDLib。
运行时状态测试进度 store、single-flight、执行 guard并发、client 隔离和清理。
数据库测试migration、引用计数、任务终态、缓存 GC使用测试锁，验证 SQLite 实际 schema。
构建检查TDLib 链接、依赖和平台兼容设置 LOCAL_TDLIB_PATH 后执行。
不要忽略已有改动 工作区可能同时包含配置、Workflow 或其他交互修改。提交前先看 git status --short 和 git diff --check，不要用 reset 或 checkout 覆盖未确认的文件。
